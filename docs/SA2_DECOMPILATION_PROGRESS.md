# SA2 Battle decompilation progress

The retail USA GameCube disc **GSNE8P, disc 0, revision 0** now has generated pseudocode for its main executable and all **95 identified REL modules**. The apploader has also been analyzed in two separate views of the same original carrier. This is an unreviewed analysis corpus, not a fully reconstructed game. The engine's existing [interactive Chao texture preview](SA2_PREVIEW.md) remains the visual test. Additive SA2 metadata and main/self relocation views now pass all 95 real modules, and the Sonic pointer-bank loader matches all 529 original-order pointer writes. The full engine build passes. A double-click data test is available alongside the texture preview; geometry, animation and full gameplay reconstruction remain unfinished.

## Original files and scope

The real ISO is 1,459,978,240 bytes. `main.dol` begins at disc offset `0x1E700`, is 1,960,448 bytes, and has SHA-256 `a53335308d1f820be236fd2b6342fee850eaf048eb26aac21ddb1903b060db2e`. Its entry is `0x80003140`; its two text sections contain 1,507,392 bytes. The fresh FST has 2,819 files. Independent Python scanning tested every raw file and prefix-decoded all 1,782 PRS files, then fully parsed each candidate module. The result exactly matches the earlier module inventory: 76 raw REL and 19 PRS-compressed REL files, all with executable sections.

The identified code-carrier count is 97: one DOL, 95 modules and one apploader. This search does not prove that ordinary assets contain no embedded code, or that runtime-generated instructions do not exist. Module identity is **disc path plus decoded SHA-256**, because ID 61 names both `ChaoMotionsD.rel` and `ChaoStgLobby.rel`. All 335 ChaoMain imports to that ID remain ambiguous. Eight original `ChaoStgLobby.rel` imports to ID 59 section 5 use addends beyond the candidate section's size; those bytes remain preserved and unbound.

The 95 modules contain 22,940,952 executable-section bytes, 102,635,025 initialized bytes and 1,754,728 BSS bytes. There are 1,664,013 relocation records and 1,662,652 actual patches: 433,275 refer to the DOL, 1,227,034 to the same module, and 2,343 to another module. Foreign patches comprise 1,582 REL24 calls, 367 ADDR32 words and 197 each HA16/LO16 halves. Full layouts and original linker behavior are in [SA2_REL_REFERENCE.md](SA2_REL_REFERENCE.md).

## Unresolved-call correction

Only proven DOL/self relocations are applied to the synthetic module images. Each stored section maps at `0x81000000 + decoded file offset`; own BSS starts at `0x81700000`. Python checked all 95 images for overlap and every main/self REL24 branch range. Their 760 embedded initialized DOL-section copies match the original bytes. Canonical module citations remain decoded REL offsets; these analysis addresses are not original runtime bases.

Unbound foreign call words encode a self-call before original runtime relocation. Ordinary Ghidra EXTERNAL references, including EXTERNAL call overrides, did not change native pcode and produced false self-loops in C. A memory call override to an explicitly artificial, uninitialized, non-executable proxy thunk at synthetic `0x90000000` preserves an unknown call without replacing any original word or inventing an original address/signature. Foreign data imports remain annotations with their bytes untouched.

The first ChaoStgDark pilot exposed a further gap: 25 foreign call sites existed, but only nine belonged to declared function bodies, while C displayed 20 unknown-call expressions. Separate controls isolated the cause. Adding an ordinary call reference alone left those counts unchanged. Explicitly disassembling each recorded call fallthrough recovered **all 25 sites, all 18 target labels and all 3,648 code bytes**; C displayed 25 call expressions and declared bodies covered 3,628 bytes. No existing body extent was manually forced, and no pointer/jump-table value was promoted to a function seed. The continuation-only variant avoids two metadata edges for each original call and was applied to the 11 modules containing foreign calls. All 11 corrected exports are complete and audited. The selected 95-module corpus has 60,320 C files and 2,530 warned functions/assembly files; all 62,850 selected artifacts passed their recorded hashes and checkpoints. One first-pass function candidate disappeared during corrected analysis, so entry count is not treated as fixed truth. Of 1,582 foreign branch sites, 21 remain without a declared function body: one in ChaoStgEntrance.prs, sixteen in ChaoStgLobby.rel and four in ChaoStgOdekake.prs, reduced from 988. ## Apploader reference

The apploader carrier starts at ISO `0x2440`: 32-byte header, 5,268-byte body and 110,048-byte trailer. SHA-256 is `75e8479dc21fc176a67668538d3cfc5ad5516c502b5db2137bd22da47980d38b`. Header entry `0x81200194` is carrier `0x1B4` / ISO `0x25F4`; it stores three callbacks into outputs addressed by r3/r4/r5: initializer `0x812001BC` (carrier `0x1DC` / ISO `0x261C`), main `0x812003EC` (`0x40C` / `0x284C`) and close `0x81200C90` (`0xCB0` / `0x30F0`). Close is an observed four-instruction block without an owning function in the initial export; it returns DOL-header word `+0xE0`, which is `0x80003140` on this real sample.

Initializer clears 32 bytes at analysis `0x81201340` and 256 bytes at `0x81201360`, zeros fields `0x81201460/1464/1468`, and stores the diagnostic callback at `146C`. Pending-read fields `1320..1330` are not explicitly cleared. Byte fill is `0x81200030` (carrier `0x50` / ISO `0x2490`). The main callback outputs destination, byte length and disc byte offset; return 1 requests another read and return 0 finishes. Its original dispatch table at `0x812012D4` has 13 internal targets, not function seeds.

| State | Original request/action | Next state / condition |
|---|---|---|
| 0,1 | Disc `0x420`, length `0x20`, destination `0x81201340` | 2 |
| 2 | Check FST length <= maximum; disc `0x440`, length `0x20`, destination `0x81201480` | 3 |
| 3 | Validate/derive memory layout; boot-info read length `0x2000` at disc `0x440` to `*0x800000F4` | 4; invalid memory/alignment halts |
| 4 | Choose FST/DOL order using DOL offset < FST offset | 5; optional FST split request |
| 5 | Read DOL header, length `0x100`, destination `0x81201360` | 6 |
| 6 | Count aligned occupied sections/FST; check limits; clear DOL BSS | 7, fallthrough |
| 7 | Read each nonempty one of seven text slots; round length to 32 | 8 after all slots |
| 8 | Read each nonempty one of eleven data slots; round length to 32 | 9 after all slots |
| 9 | Read deferred FST if DOL precedes it | 10 |
| 10 | Write metadata at `0x80000020..3C`, including `0xD15EA5E`, version 1 and FST pointers | 11, fallthrough |
| 11 | Write hardware-derived halfword at `0x800030E4` | Return 0 |
| 12 | Continue split read only when pending flag is 1 | Restore saved request/state; otherwise halt |
| default | Invalid state | Return 0 |

The split helper `0x81200100` (carrier `0x120` / ISO `0x2560`) splits only lengths greater than `0x20000`; it saves remaining destination/length/disc offset/state and enters state 12. Failure loop `0x81200CA0` is carrier `0xCC0` / ISO `0x3100`. Cache helpers `0x81200CB4`/`0x81200CE4` (`0xCD4`/`0xD04`, ISO `0x3114`/`0x3144`) operate 32-byte blocks, increase counted length by 32 for unaligned addresses, and return immediately for zero length. The real DOL has two nonempty text and six nonempty data slots; this validates the sample header, not boot execution.

The trailer begins at carrier `0x14B4` / ISO `0x38F4`. Original register literals set `r1=0x81328DE0`, `r2=0x81321760`, `r13=0x81321480`; absolute literals support a separate linked-address analysis view at `0x81300000`, now also supported by the original DOL load-and-transfer path below. Python verified all 110,048 trailer bytes against the real ISO and seven bootstrap transfers/six direct calls. No BSS or external original bytes were invented. The header/init/main/close trace contains no explicit trailer-copy/invocation operation in that inspected path. A separate original DOL routine does load and enter the trailer; successful execution and its outer trigger remain unobserved. Both views cite the same original carrier offsets and must be deduplicated.

Initial trailer FPSCR sites at analysis `0x81204728`/`0x812048C8` correspond to carrier `0x4748`/`0x48E8`, ISO `0x6B88`/`0x6D28`. In the separate linked view, restore function `0x81303284` (carrier `0x4738`, ISO `0x6B78`) contains writer `0x81303294`; save function `0x813033A8` (carrier `0x485C`, ISO `0x6C9C`) contains reader `0x81303434`. Python verified all 411 checkpoints/610 artifacts and 66 original FP-sensitive words: 32 each `psq_l`/`psq_st`, one `mtfsf`, one `mffs`. Restore C drops architectural FPR/FPSCR assignments and uses opaque quantization calls; these are context save/restore operations, not literal startup controls. All Gekko FP qualifications apply. The two views have 405 shared entry offsets, ten initial-only and six linked-only, yielding 421 unique carrier offsets.

## Original trailer load and architectural effects

Original DOL function `0x800E8C40` (DOL `0xE5C40`) requests the 32-byte header at disc `0x2440` into `0x802BA940` through `0x800F1174` (DOL `0xEE174`), call site `0x800E8D10` / `0xE5D10`. Original loads at `0x800E8D58`/`0x800E8D5C` use header `+0x18` trailer size and `+0x14` body size. Instructions through `0x800E8D94` derive `((trailer_size+31) modulo 2^32)&0xFFFFFFE0` and `(body_size+0x20+0x2440) modulo 2^32`, then request that length from that disc offset into `0x81300000`. The single Python validation run verified 143 original words and the real sample: **110,048 bytes from disc `0x38F4` through `0x1E6D4` exclusive**, no padding, exactly the prepared trailer payload. SHA-256 is `e9c338af6fbb598f7f53cf752d4e50a997e2bda6e26e9e0989bc56336acbe05f`. Generated C incorrectly folds this into length zero/disc `0x2460`; the original words and actual header arithmetic are authoritative. The cause of that folding is not established.

After status checks and instruction-cache invalidation through `0x800E4F14` (DOL `0xE1F14`), call site `0x800E8DEC` / `0xE5DEC` passes `0x81300000` to `0x800E8BF4` / `0xE5BF4`. That helper saves incoming r3 in r31 at `0x800E8C04` / `0xE5C04`, calls two helpers that preserve r31, writes **LR=r31** at `0x800E8C18` / `0xE5C18`, then branches through LR at `0x800E8C1C` / `0xE5C1C`. Its C prints an ordinary return and loses the target input and transfer. Five following cleanup words are outside the selected body and remain unclassified. Callback words at `0x800E8C34` / `0xE5C34` set SDA `-0x7620` to one; actual readiness and caller purpose are not observed. This proves a static destination-and-transfer path, not successful DVD I/O or execution.

The called helper `0x800E78AC` / DOL `0xE48AC` performs `mfmsr`, mask `0xFFFF7FFF`, `mtmsr`; `0x800E4F4C` / `0xE1F4C` performs HID0 read, OR `0x800`, HID0 write. Their generated C loses the writes. All three specific transfer/register-write C samples have completed status, no recorded warning and no retained assembly in the primary main export. A project-free Python encoding scan covered 97 carriers / 6,140,915 aligned words once: 58,857 explicit LR writes, 36 MSR writes, 43 RFI MSR-restoration encodings, 13 HID0 writes. These are instruction-encoding matches, not execution or blanket failure counts. Ordinary LR epilogs are not missing-call findings. Exact source words and C hashes are retained in the architectural evidence; warning-free C remains unreviewed.
